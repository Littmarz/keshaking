# Передача работы по агенту и локальной LLM

## Этап 1. Поиск по регламентам

- Командный поиск из `a973e71` подключён в режиме `AGENT_MODE=real AGENT_SOURCES=documents`. Docker по умолчанию использует BM25. Агент передаёт модели до пяти найденных пунктов, в ответе сохраняет номер пункта и исходную цитату. В показателях ответа появляются число найденных пунктов, балл первого результата и число проходов поиска.
- После уточнения агент ищет по исходному вопросу и ответу на уточнение. Если в уточнении распознана одна дирекция, поиск фильтруется по ней.
- Четыре DOCX кладутся локально в `data/raw/`. В Git и образ Docker они не входят. [Команда запуска](../deploy/punkt-demo.md). Учебный режим остаётся доступен через `AGENT_SOURCES=demo`.
- Проверено на сборке `0.0.3` через API чата с Ollama. Qwen назвала аккаунт-менеджера со ссылкой на п. 1.2 Техдирекции и применила включительную границу 30% со ссылкой на п. 1.3 пресейла ИБ. Прошли 8 тестов поиска и 5 тестов числовых условий. В контрольном наборе поиск нашёл ожидаемый пункт в первых пяти результатах в 13 из 14 оцениваемых сценариев. Пропуск — `c13`, вопрос о сроке расчёта ДБРЦТ.

## Этап 2. Служба качества

- Новые обращения ставятся в очередь уведомлений SQLite вместе с сохранением чата. При включённом тестовом профиле почта приходит в локальный Mailpit. Повтор вопроса в том же чате использует исходное обращение. Ответ эксперта вводится и подтверждается в «Пункте». [Запуск тестового ящика](../deploy/punkt-demo.md#служба-качества-с-тестовым-почтовым-ящиком).
- В режиме документов поиск BM25 отдельно подбирает до трёх подтверждённых разъяснений по исходным вопросам в SQLite. Черновики и явно несовпадающие дирекции отфильтровываются до запроса к модели. Модель проверяет область применимости и получает указание цитировать применимое разъяснение при конфликте с регламентом.
- На сборке `0.0.4` проверено через API: вопрос о сроке в Техдирекции создал обращение и письмо в Mailpit. Повтор в том же чате сохранил номер и количество писем. Черновик не цитировался, после подтверждения Qwen ответила на перефразированный вопрос в новой сессии с цитатой из разъяснения. В отдельном тесте с учебным противоречием Qwen процитировала разъяснение вместо п. 1.2 Техдирекции.
- В одном перефразированном вопросе до публикации разъяснения Qwen выбрала `refused` при отсутствии правила, хотя по контракту нужен `escalated`. В контрольном прогоне добавить варианты формулировок, проверяющие это различие.
- Следующий этап — контрольный прогон на Mac с 24 ГБ, включая ответ с цитатой, уточнение и службу качества. Замерить задержку и токены на запрос.

## Учебный режим и числовые правила

- В режиме `AGENT_MODE=real` чат «Пункт» вызывает Qwen3 8B через нативный API Ollama `/api/chat`. Ollama работает на хосте, backend и frontend запускаются в Docker Compose. [Как запустить](../deploy/punkt-demo.md).
- Текущий агент получает учебные пункты и подтверждённые записи из очереди службы качества. Он возвращает ответ с цитатами, вопрос для уточнения, направление в службу качества или отказ. Обращение создаёт backend. Повтор того же вопроса в одной сессии не создаёт дубликат.
- Для распознанных порогов Python вычисляет строгое или нестрогое сравнение. В паре соседних альтернатив модель получает подходящую числовую ветку. Цитата в интерфейсе берётся из исходного пункта. Если для правила в рабочих днях указан только календарный срок, агент уточняет число рабочих дней.
- Счётчики входных и выходных токенов доступны в `steps[].detail`. В журнале расчёта стоимости использовать данные финального сквозного прогона.

## Проверки до подключения поиска

- На учебных источниках через API чата проверены ответ с цитатой, уточнение дирекции, создание обращения, повтор без дубликата и применение ответа после подтверждения. Эти проверки проходили до последнего изменения числовых правил.
- После изменения порогов прошли пять модульных тестов и девять вызовов Qwen с вручную переданными выдержками из двух регламентов. Проверены 4, 5 и 6 рабочих дней, возврат карточки в работу, 29%, 30% и 31%, неизвестный статус хардоффера и календарные дни. Полная загрузка DOCX и поиск в этот прогон не входили.

Запуск модульных тестов из `backend/`:

```bash
uv run --python 3.12 python -m unittest discover -s tests -v
```

## Ограничения, которые важно проверить

- Распознавание порогов поддерживает числа цифрами, проценты и явно указанные рабочие дни. Числа словами, другие форматы, несколько значений одной единицы и произвольная вложенность пока требуют отдельных тестов. Если правило не распознано, модель может неверно применить порог даже при верной цитате.
- Для процентных веток отдельно проверять отсутствие подходящего хардоффера, явный отказ от услуг и ситуацию, когда известна только доля. Текущие положительные тесты вокруг 30% задавали остальные условия явно. Тест с неизвестным хардоффером проверял уточнение. Отказ от услуг и смешанные вопросы ещё предстоит проверить.
- Проверка идентификатора цитаты подтверждает существование источника, но не соответствие каждого вывода тексту. В оценке сверять выбранный пункт, значение на границе и условия применимости отдельно.
- Клиент использует нативный API Ollama. Для другого сервера инференса проверить его совместимость на уровне API и формат подсчёта токенов.

Публикуем код, документацию и синтетические тесты. Материалы заказчика храним в локальной папке данных. [Правила команды](04-workflow.md).
